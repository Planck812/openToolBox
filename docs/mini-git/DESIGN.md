## 1. 设计目标与约束

### 1.1 需求侧约束

| 来源 | 约束 | 对设计的影响 |
| --- | --- | --- |
| G4 / NFR-3.2 | 严格只读，只读挂载的仓库仍可全功能运行 | 禁用一切写入类 API；不生成 commit-graph、不回写索引缓存；性能设计不能依赖这两类缓存 |
| NFR-4.2 | 不依赖用户系统安装 Git 命令行 | 采用 libgit2 绑定，不 shell out |
| NFR-5.5 | 异常不得导致宿主进程退出 | 宿主 release 配置为 `panic = "abort"`，一次 panic 即终止整个进程。错误处理必须全程 `Result` 化，由 lint 强制 |
| FR-8.4 / FR-8.5 | 关闭即隐藏、状态完整保留 | 窗口生命周期走「拦截关闭 + 隐藏」，webview 不销毁 |
| NFR-1.1a | 宿主已运行时新建窗口 ≤ 1.0 秒 | 独立精简入口，不加载宿主的工具注册表 |
| FR-10.1 / FR-10.2 | 仓库资源经受限协议访问；大内容不走 JSON 通道 | 新增专用自定义协议，不放宽全局资源作用域 |

### 1.2 宿主侧既有能力

| 能力 | 现状 | 复用方式 |
| --- | --- | --- |
| 多窗口 | 已有独立 Vite 入口 + Rust 侧窗口构建的成熟模式 | 沿用，新增 Mini-Git 入口 |
| 自定义协议 | 已有图片类自定义协议的实现先例 | 沿用其注册与鉴权结构 |
| 类型化 IPC | tauri-specta 自动生成前端绑定 | 新增命令接入既有的宏链。**注意有两套独立的宏链**：类型导出一套（两个条件编译分支都要加），运行时命令分发另一套（累加器链式宏）。只加前者会得到「有类型但调用报命令不存在」 |
| 主题与国际化 | 统一的主题令牌与双语资源，经同源本地存储在窗口间共享 | 读取可复用。**但跨窗口即时生效的广播机制宿主目前不存在**——现有窗口靠同源存储在自身初始化时读取。需求要求切换后即时生效且隐藏态窗口在下次显示前完成应用，这条是**新增工作量而非复用** |
| 全局快捷键 | 已有快捷键注册与同步模块 | 新增一条工具快捷键 |
| 单实例 | 已集成单实例插件 | 无需改动 |
| 自绘标题栏 | 主窗口已为无边框 + 自绘 | 复用其组合式函数与样式 |
| 配置持久化 | 宿主应用配置走同源本地存储；另有独立文件存储的先例（便利贴数据） | **主题与语言继续读同源本地存储**（共享是正当的）；**Mini-Git 自身的持久化数据走独立文件存储**。两个理由：同源本地存储的配额由宿主全应用共用，十个仓库会话的展开集合与已查看标记有撑爆共享配额、连带影响宿主其他工具的风险；且其路径不可注入，与测试所需的配置目录隔离互斥 |

### 1.3 明确的设计取舍

| 取舍 | 选择 | 代价 |
| --- | --- | --- |
| 差异计算位置 | 后端返回两侧完整文本 **+ hunk 边界**，前端只在 hunk 内做行配对与行内高亮 | 底层库提供 hunk 边界但不提供行对齐、行内差异、折叠区原文。沿用其 hunk 划分可避免用另一种语言重算同一算法，前端代价对变更行数而非文件行数线性 |
| 换行处理 | 比较前统一将 CRLF 折为 LF | 不区分纯换行风格的改动 |
| 提交遍历顺序 | 时间序 | 不保证严格拓扑序；时钟异常的提交可能与父提交顺序颠倒 |
| 仓库句柄 | 每个工作线程独占一份句柄 | 多开几份句柄换取互不阻塞；打开成本毫秒级 |
| 后端状态 | 仅保留两类：会话资源（句柄、游标、取消标志）与差异内容令牌缓存。业务数据缓存全部在前端 | 后端不承担业务数据的失效管理；令牌缓存有明确的容量与有效期边界（见 5.9.1） |

## 2. 架构总览

### 2.1 进程与窗口

```
Open-Toolbox 进程
├─ 主窗口（index.html）            现有，27 个工具的宿主
├─ 快速唤起窗口                     现有
├─ 便利贴 / 贴图 / 计时等窗口        现有
└─ Mini-Git 窗口（mini-git.html）   新增
     label: "mini-git"（单例）
     关闭 → 拦截并隐藏，webview 不销毁
     任务栏可见，可 Alt+Tab 切换
     复用宿主 WebView 运行环境，不设独立数据目录
```

复用宿主 WebView 环境是明确决策：独立数据目录会额外产生数个进程与数百 MB 峰值内存，而共享环境只多一个渲染进程。这同时是主题与国际化通过同源存储共享的前提。

### 2.2 模块边界

```
src-tauri/src/
├─ resident/          新增：通用常驻窗口管理（不限于 Mini-Git）
│   ├─ mod.rs            窗口注册表、生命周期、单例保障
│   └─ commands.rs       resident_open / resident_focus
└─ minigit/           新增：Git 只读读取
    ├─ mod.rs            命令导出
    ├─ types.rs          serde + specta 类型
    ├─ error.rs          错误码与转换
    ├─ repo.rs           仓库校验、打开、HEAD、中间态
    ├─ tree.rs           目录列举、忽略集合批量判定
    ├─ refs.rs           引用枚举与分组
    ├─ log.rs            提交遍历（持久游标）、搜索
    ├─ diff.rs           提交差异、工作区差异、hunk 与完整文本
    ├─ blob.rs           文件内容读取、二进制与编码判定
    ├─ status.rs         工作区状态扫描
    ├─ protocol.rs       mini-git 自定义协议
    └─ session.rs        仓库句柄管理与长任务调度

src/
├─ mini-git-main.ts    新增：独立入口
└─ mini-git/           新增：前端模块
    ├─ App.vue            根组件（标题栏 + 路由出口）
    ├─ router.ts          两个路由：picker / workspace
    ├─ stores/            repos / session / gitdata / tabs
    ├─ views/             RepoPickerView / WorkspaceView
    ├─ components/        文件树、标签页、查看器、差异、Git 面板
    └─ lib/               纯函数：模糊匹配与打分、自然排序、差异行配对、
                          行内词级高亮、Markdown 净化、时间格式化、
                          引用树分组构造、差异投影器（供真值比对）
```

`resident/` 独立于 `minigit/`，是为了让后续其他重型工具能复用同一套常驻窗口机制。

### 2.3 分层职责

| 层 | 职责 | 不做什么 |
| --- | --- | --- |
| Rust 命令层 | 参数校验、调度到阻塞线程池、错误码转换 | 不做业务缓存 |
| Rust 数据层 | 调用底层库读取仓库，产出结构化数据 | 不持有跨请求的可变状态（句柄除外） |
| 自定义协议 | 大内容的原始字节传输与路径鉴权 | 不做业务逻辑 |
| 前端 store | 数据缓存、会话状态、持久化 | 不直接调用底层 API |
| 前端纯函数库 | 匹配打分、自然排序、差异行配对、行内高亮、净化、时间格式化、引用分组、差异投影 | 不依赖组件与 DOM；**不做编码与二进制判定**——该职责唯一归属后端 |
| 前端组件 | 渲染与交互 | 不做复杂计算 |

纯函数库单列是测试策略的要求：这八类逻辑需在前端单测层以表驱动方式全覆盖，不能耦合组件。

**编码与二进制判定只在后端实现一份**。该判定需要读取文件原始字节并按既定算法裁决，前端拿到的已是判定结果。两处各实现一份必然漂移。

**差异投影器**是真值比对的专用组件：把差异结构投影为 `(旧行号, 新行号, 类型, 内容)` 序列，以便与 Git 的 patch 真值逐行对齐。它自身必须有单测——投影器的缺陷会静默掩盖真实差异，产出一堆假通过，比不测更糟。

## 3. 技术选型

| 领域 | 选型 | 理由 | 被否决的方案 |
| --- | --- | --- | --- |
| Git 读取 | libgit2 的 Rust 绑定，`default-features = false` | 不依赖系统 Git；关闭默认 features 可去掉 HTTPS 与 SSH 传输层，避免引入 TLS 与 SSH 依赖，同时让依赖审计可通过 | 调用 Git 命令行：需用户安装、输出解析脆弱、跨平台编码问题多 |
| 语法高亮 | CodeMirror 6（Lezer，纯 JS），语言包按需动态加载 | 宿主已有该依赖；纯 JS 不触发 WASM，与现有内容安全策略兼容 | 基于 WASM 正则引擎的方案：宿主脚本策略不含 WASM 执行权限，为此放宽全局策略得不偿失 |
| Markdown | markdown-it + DOMPurify | 宿主已有两者；净化是硬需求 | 其他渲染器：需新增依赖 |
| 差异算法 | 后端出完整文本 + hunk 边界，前端只在 hunk 内细化 | hunk 划分沿用底层库结果，与真值天然一致；前端只承担行对齐与行内高亮这两项底层库不提供的能力 | 前端全文件重新配对：需用另一种语言复现同一算法才能与真值对齐，且代价随文件行数增长 |
| 虚拟滚动 | 固定行高的自实现 | 提交行需等高才能保证滚动流畅度指标；需求简单 | 通用虚拟列表库：引入体积且需适配等高约束 |
| 持久化 | 宿主既有的本地配置读写层 | 与宿主一致，同源共享 | 独立存储：与主题共享机制不一致 |

### 3.1 语法高亮的语言范围

首版支持：JavaScript、TypeScript、JSON、HTML/Vue、CSS、Rust、Python、Go、Java、Shell、Markdown、YAML、TOML、XML、SQL、C/C++。

清单外扩展名以纯文本加行号呈现。无扩展名文件按文件名识别（Dockerfile、Makefile、LICENSE 等）。语言包以动态导入分块，不进主包。

## 4. 常驻窗口机制

### 4.1 工具形态扩展

在工具元数据中新增可选字段，区分「窗口内路由页」与「独立常驻窗口」两种形态：

```ts
interface ToolMetadata {
  // ...existing
  /** 'inline'（默认）：主窗口内路由页；'window'：独立常驻窗口 */
  mode?: 'inline' | 'window';
}
```

首页与快速唤起在点击工具时判断该字段：`mode === 'window'` 时调用 `resident_open(toolId)` 打开窗口，不进行路由跳转。工具仍正常注册，搜索、收藏、最近使用等既有能力不受影响。

### 4.2 窗口参数

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `label` | `mini-git` | 单例判重 |
| `inner_size` | 1400 × 900 | 审阅场景需要较大版面 |
| `min_inner_size` | 1000 × 600 | 三区布局的最小可用尺寸 |
| `decorations` | `false` | 复用宿主自绘标题栏 |
| `skip_taskbar` | `false` | 必须可通过系统窗口切换到达 |
| `always_on_top` | `false` | 非浮层 |
| `resizable` / `maximizable` | `true` | |
| 拖放处理器 | **保持默认（由框架拦截）** | 注意语义方向：禁用框架的拖放处理器等于把文件拖放**放行**给网页层。保持默认才是拦截。拖放这条写入通道由三层兜住：框架拦截 + 前端不监听拖放事件 + 编辑器只读 |
| `data_directory` | 不设置 | 复用宿主 WebView 环境 |

### 4.3 生命周期

```
resident_open(tool_id)
  ├─ 窗口已存在 → show() + unminimize() + set_focus()
  └─ 不存在     → 构建窗口（守卫：get_webview_window(label).is_none()）

WindowEvent::CloseRequested（label == "mini-git"）
  └─ api.prevent_close() + window.hide()

宿主退出（app.exit）
  └─ 走退出请求路径，进程直接退出，不逐窗口触发关闭事件
```

不提供独立的「彻底退出」入口。销毁 webview 会清空内存状态，与「关闭后唤起状态不变」的目标冲突；托盘已有整体退出。

**标签竞态**：若未来需要销毁重建，销毁事件与标签从注册表移除不同步，同一事件循环内立即重建会撞标签冲突。构建前必须以「窗口不存在」为守卫，或等待销毁事件到达。宿主已有同类清理的先例可循。

### 4.4 唤起入口

| 入口 | 实现 |
| --- | --- |
| 首页工具卡片 | 点击时按 `mode` 分流 |
| 托盘菜单 | 菜单新增一项，回调调用 `resident_open` |
| 全局快捷键 | 接入宿主既有的工具快捷键同步机制，默认组合可在设置页修改 |

## 5. 后端设计

### 5.1 并发模型

底层库全部为同步阻塞 API。所有命令声明为异步，实际工作在专用线程中完成，不占用界面事件循环。

#### 5.1.1 为什么不用「互斥表持有仓库句柄」

直觉方案是把仓库句柄放进一张互斥保护的表里按需借用。该方案有两处落不了地：

1. **遍历器借用了仓库句柄**。提交遍历器的类型带有仓库的生命周期参数，它不能脱离仓库句柄独立存在。而持久游标要求遍历器跨多次进程间调用存活——放进互斥表意味着需要自引用结构，实现复杂且易错。
2. **长任务会堵死交互**。全量搜索在大档仓库上耗时数秒，与文件树展开共用同一把锁时，所有交互请求会排队等待。

#### 5.1.2 采用：每会话一个工作线程（actor 模型）

每个会话持有一组工作线程，**每个线程独占自己的一份仓库句柄**。打开句柄的成本是毫秒级，多开几份换取互不阻塞是划算的。

```
RepoSession（每个已打开仓库一个）
├─ nav 线程      导航类：目录列举、引用枚举、提交遍历、提交详情
│                  持久游标在此线程内创建与持有，永不跨线程
├─ status 线程   工作区状态扫描（成本与工作区文件数相关，可达数秒）
├─ diff 线程     单文件差异计算；持取消标志
└─ task 线程池   长任务：全量搜索、超大差异；按需创建，可并存
                   各自独立句柄 + 独立取消标志
```

**线程划分依据是「会不会互相拖慢」而非功能分类**：首屏的三路请求分别落在 nav、nav、status 上——引用枚举与首批提交同属导航类且都在百毫秒内，串行无妨；而状态扫描可达 1.5 秒，必须与导航类分离，否则会把首屏堵死。差异计算单列是因为它需要可中止，而中止一个正在服务其他请求的线程会误伤。

游标必须固定在创建它的线程上：遍历器与其句柄同属一个线程栈，跨线程访问在类型系统上不成立。命令层按游标标识路由到 nav 线程。

**唯一可行的写法是把句柄与游标表都作为工作线程主函数的局部变量**，且游标表须声明在句柄之后（局部变量的析构顺序是声明的逆序，游标必须先于句柄释放）：

```
fn worker(path, rx):
    let repo = 打开仓库(path)          // 先声明
    let mut walks = 游标表              // 后声明，先析构
    while 收到请求: 处理
```

**不能把二者封进同一个结构体**——游标类型带有对句柄的借用，自引用结构在类型系统上不成立。这是实现时最容易先写错再卡住的地方，须在动工前明确。

该模型同时解决四个问题：

| 问题 | 解决方式 |
| --- | --- |
| 仓库句柄可移动但不可共享 | 句柄始终由单一线程独占，从不跨线程共享 |
| 遍历器的生命周期 | 遍历器与其仓库句柄同在一个线程内，不跨调用边界传递；对外只暴露一个不透明的游标标识 |
| 长任务阻塞交互 | 长任务在独立线程与独立句柄上运行，与主工作线程无锁竞争 |
| 取消 | 分情况：提交遍历与差异**遍历**由我方逐条驱动，可在两次推进之间检查取消标志并退出；**工作区状态扫描与差异生成不可取消**——底层只提供一次性返回的接口，没有逐项回调。对这两类，「取消」的实际含义是丢弃结果、不再回送，线程仍需跑完 |

命令层持有的是会话标识与游标标识，通过通道与工作线程通信；Tauri 托管状态中只保存标识到通道发送端的映射，本身是线程安全的。

**每个请求携带自己的一次性回复通道**，不使用共享回包通道。否则一旦某个请求超时被丢弃，后续回复会与请求错位，产生极难定位的串扰。

**调度带亲和性**：携带游标标识的请求必须路由到持有该游标的线程；无游标的请求走空闲线程。这保留了「句柄单线程独占」与「游标不跨线程」两条不变量，同时消除队头阻塞。

#### 5.1.3 后端会话与游标的生命周期

> **术语消歧**：本节的「**后端会话**」指工作线程组与仓库句柄这组运行时资源，上限 3 个。需求文档中的「**仓库会话**」（FR-2.4）指持久化的界面状态，上限 10 个。二者不是一回事——后端会话在切换仓库时释放，而持久化的仓库会话会一直留在磁盘上等待下次进入。全文其余位置按此区分。

| 资源 | 创建 | 释放 |
| --- | --- | --- |
| 后端会话（工作线程组 + 仓库句柄） | 进入仓库时 | 切换仓库时释放最久未用的；上限 3 个并存 |
| 游标 | 打开提交列表或切换过滤条件时 | 过滤条件变更、切换 Tab、切换仓库、会话释放时；同一会话内同时存活的游标上限 4 个，超出按最久未用释放 |
| 长任务线程 | 发起搜索或超大差异计算时 | 任务完成、被取消、或会话释放时 |

**窗口隐藏时不释放会话**——「唤起即恢复」要求状态完整保留，重新打开仓库会带来可感知的延迟。会话的内存占用主要是句柄本身，可接受。

**防泄漏**：所有游标与长任务在会话释放时强制回收；前端在组件卸载与仓库切换时显式关闭游标；后端对超过 10 分钟未被访问的游标做兜底回收，避免前端异常退出造成堆积。

#### 5.2.1 关键入参结构

```rust
struct LogFilter {
    /// 完整引用全名（如 refs/heads/v1.0）。同名分支与标签必须靠全名区分，
    /// 传简名会导致解析歧义。None 表示当前 HEAD。
    refname: Option<String>,
    author_contains: Option<String>,
}

struct SearchQuery {
    text: String,
    /// 搜索范围继承引用过滤，与过滤条件构成「与」关系。
    refname: Option<String>,
    author_contains: Option<String>,
}
// 哈希前缀匹配：text 长度 ≥ 4 且为合法十六进制时，额外按哈希前缀匹配；
// 长度不足 4 时只按提交信息全文匹配。

enum DiffSource {
    /// HEAD 与工作区对比，不区分暂存层
    Working,
    /// 未跟踪文件：左侧为空树，右侧取工作区内容
    WorkingUntracked,
    /// 冲突文件：不做对比，直接返回工作区原始内容（含冲突标记）
    WorkingConflicted,
    Commit(String),
}
```

`WorkingUntracked` 与 `WorkingConflicted` 必须单列：未跟踪文件不在 HEAD 与工作区的差异集合内，冲突文件需要的是原始内容而非对比结果，二者都无法由 `Working` 这一种来源表达。

#### 5.2.2 提交排序的二级键

时间序遍历对 committer date 相同的提交不保证稳定顺序。需在取出每一批后按 `(committer_date DESC, oid ASC)` 做二级排序，保证多次读取结果完全一致。排序在批内进行，不影响游标的增量语义。

`mg_diff_prepare` 的返回体现三档模型：完整档返回两侧内容令牌（凭令牌经协议取原始字节），退化档返回 unified hunk，放弃档只返回统计。

### 5.3 忽略判定与目录列举

**实现方式**：单次状态查询调用，配合下列选项，而非逐条目调用单文件状态查询——后者内部会以最重的一组标志跑完整扫描，且对目录条目直接返回错误，5000 条目逐条调用不是慢而是不可用。

| 选项 | 取值 | 作用 |
| --- | --- | --- |
| 路径限定 | 目标目录路径，**必须带尾部分隔符** | 使文件系统迭代器按目录前缀剪枝，代价为子树而非全仓 |
| 字面量路径匹配 | 开启 | 走字面量语义，配合上一条生效 |
| 递归未跟踪目录 | 关闭 | 避免进入未跟踪目录内部 |
| 递归被忽略目录 | 关闭 | 避免进入大型依赖目录 |
| 包含被忽略项 | 开启 | 同一次调用即可拿到本级的忽略集合 |
| 索引刷新 | 关闭 | 只读约束 |

这样一次调用同时得到本级的条目状态与忽略集合，忽略判定无需另走一条路径——而底层并不存在「一次调用取整级目录忽略集合」的接口，逐条目判定会重复构建规则栈。

**「已跟踪文件不隐藏」在此方案下是白送的**：已跟踪文件本就不会被报为忽略项，无需额外的索引查找修正。

**目录的忽略判定必须带尾部分隔符**，否则只匹配目录的规则会漏判。

**根目录是例外**：路径限定对根目录等于没有剪枝，一次根目录列举就是全仓扫描，与状态扫描同量级。因此根目录列举**只返回条目与忽略判定，不附带状态**，状态一律由首屏的第三路异步填充。

这是性能最敏感的一处，还有三条硬约束：

1. **按整级目录批量判定**，不按条目跨进程往返。5000 次往返需数秒。
2. **不通过枚举全仓库忽略集合的方式求取**——那会递归进入被忽略目录内部，比逐级判定贵一到两个数量级。
3. **已跟踪文件即使命中忽略规则也照常返回**。底层的忽略判定只做规则匹配，不检查跟踪状态；已被加入索引后才写进忽略规则的文件会被误判，用户会以为文件丢失。需额外做一次索引查找修正。

默认隐藏被忽略项不只是界面收益：隐藏后大型依赖目录根本不会被展开，连目录读取都省去。真正的耗时大头是目录读取与文件元数据获取，而非规则匹配。

忽略规则的判定范围须覆盖嵌套忽略文件、仓库内的排除文件，以及配置指向的**全局忽略文件**——后者位于仓库目录之外，属于读取范围内明确允许的 Git 标准配置。

**文件树的变更状态徽标不在此处产生**。状态扫描的结果由前端缓存，渲染时按路径叠加到树节点上；扫描未就绪时该列留空。父目录的后代变更数在前端由状态路径集合一次性预计算为映射表，不逐目录回查后端。这与「改动数角标允许延迟出现」的首屏策略一致。

### 5.4 提交遍历

```
mg_log_open  → 建立游标，按时间序排序
mg_log_next  → 在同一游标上增量推进 N 条
mg_log_close → 释放
```

两条约束：

- **禁用拓扑排序**。拓扑排序需要大范围预遍历，在大档仓库上耗时为秒级。
- **禁止每页重建遍历器后跳过前 N 条**。第 100 页需跳过一万条，耗时随页码线性增长。

#### 5.4.1 时间序的首次推进代价

底层遍历器一旦设置排序方式（含时间序），内部会进入「受限模式」：**第一次推进就要把全部可达提交解析并入优先队列**，此后每次推进才是常数代价。

这意味着：

| 阶段 | 代价 |
| --- | --- |
| 游标建立后第一次推进 | O(全部可达提交)，大档仓库上为秒级 |
| 第二页及以后 | 常数级，与页码无关 |

「翻页耗时不随页码增长」这一设计意图**仍然成立且可验证**，但「首批 100 条只需解析少量对象」的假设**不成立**。

**由此调整首屏策略**：提交列表的首批加载从首屏同步路径中移出，与工作区状态扫描同等对待——首屏只保证引用树与文件树就绪，提交列表异步填充并展示骨架。这与「三路互不阻塞」的原则一致，也是改动面最小的方案。

被否决的替代方案：不设排序走真增量遍历——虽然首次推进变为常数级，但跨分支不再按时间排序，与需求定义的展示顺序冲突。

#### 5.4.2 遍历计数的语义

`LogPage` 返回两个计数，用途不同：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `walked` | 本次推进从队列取出的提交数 | 验证「不随页码增长」——第 2 页起应恒为页大小量级 |
| `parsed` | 本次调用解析的提交对象数 | 首次推进会远大于页大小（见 5.4.1），此后接近 0 |

两个计数分开暴露，测试才能分别断言增量语义与首次代价，不至于把二者混为一谈。

**断言时须注意过滤条件的影响**：启用引用或作者过滤时，被过滤掉的提交也计入遍历数，遍历数与返回数天然不等。只有无过滤时才能断言二者严格相等；有过滤时应断言「遍历数不随页码增长」这一趋势，而非某个精确值。

`mg_log_next` 的返回值携带「本次遍历的提交数」，使「耗时不随页码增长」这一设计意图可以用确定性的计数断言验证，而非依赖易抖动的墙钟断言。

### 5.5 差异生成

```
mg_diff_prepare(source, rel_path)
   source ∈ { Working, Commit(oid) }
        │
        ├─ 判定规模
        │    完整档：两侧总行数 ≤ 20 000 且各侧 ≤ 2 MiB
        │    退化档：两侧总行数 ≤ 200 000 且各侧 ≤ 20 MiB
        │    放弃档：超出，或任一侧为二进制
        │
        ├─ 完整档 → 取两侧完整文本 → CRLF 折为 LF → 缓存并返回内容令牌
        ├─ 退化档 → 返回 unified hunk（仅行级）
        └─ 放弃档 → 返回统计与原因
```

**换行归一化必须在后端完成**。对象库中存储的是 LF，工作区文件可能是 CRLF；若直接取两侧原文比较，在启用自动换行转换的仓库上每一行都会被判为已修改。

两种实现路径：

| 路径 | 说明 | 采纳 |
| --- | --- | --- |
| 走底层库的 blob 过滤接口取过滤后内容 | 完全遵循仓库的换行与属性配置，与命令行工具结果一致 | 备选，**该接口是否已被 Rust 绑定层暴露需在阶段 1 实测确认** |
| 比较前统一将 CRLF 折为 LF | 实现简单，对只读查看器足够 | **默认采用** |

默认采用折叠方案，代价是不区分纯换行风格的改动，此取舍已在需求侧确认。阶段 1 实测若确认过滤接口可用，可作为增强项切换，届时需同步调整真值比对的对齐口径。

与 Git 真值比对时，差异算法必须固定为 Myers（底层库默认亦为该算法），并对齐重命名阈值与前缀设置，否则同一份改动会产出不同但都正确的划分，逐行比对将大面积假阳性。

**重命名检测**：阈值 50%，关闭复制检测。

三点必须写死的行为：

| 项目 | 说明 |
| --- | --- |
| 上限必须显式设置 | 不显式设置时，底层会读取用户的本地配置，行为随用户环境漂移——这与「与 Git 真值逐行比对」的确定性测试策略直接冲突。取值 200：底层默认值为 1000，而相似度计算的代价随上限增长，200 在准确度与耗时之间更平衡 |
| 失效模式是**部分漏检**而非整体放弃 | 超限时是「每个目标最多考察 N 个候选后跳出」，靠后的目标可能错过最佳匹配，**不是全部退化为删除加新增**。需求与用例中按「全漏」描述的部分需同步修正 |
| 超限提示须自行判定 | 底层不提供超限的出参、回调或警告通道。需在调用检测**之前**统计本次差异中新增与删除条目的数量，据此决定是否向界面返回提示 |

### 5.6 只读约束的落地

| 手段 | 内容 |
| --- | --- |
| **关闭所有权校验** | 底层库默认开启仓库所有权校验，仓库不属于当前用户时**直接拒绝打开**。只读挂载、网络共享、容器绑定挂载、跨子系统路径都会踩中。这不是性能问题而是根本打不开，会让「只读挂载仍可全功能运行」的验收直接失败。须在初始化时一次性关闭该校验——本模块纯读，理由充分。注意该开关是**进程全局**的，需在文档与代码注释中标明 |
| 显式关闭写入选项 | 状态查询与差异计算的索引更新选项必须显式设为关闭，**不依赖库的默认值**——绑定层的默认值在版本间变动过 |
| 禁用 API 清单 | 仓库发现（向上遍历父目录）、索引写入、树写入、HEAD 设置、引用写入、检出类、储藏类、commit-graph 写入 |
| 打开方式 | 必须按精确路径打开。向上遍历会在用户选择子目录时静默打开父仓库，既违反判定规则也违反读取范围约束 |
| 强制手段 | 一个专用的集成测试扫描模块源码（跳过注释与测试块）对清单断言，给出文件与行号 |

底层库的忽略与属性缓存为纯内存实现，不落盘；打开仓库本身不写任何内容；读取引用不会重写打包引用文件。只要守住上述清单，只读挂载的仓库可以完整运行。

**代价须记录在案**：不生成 commit-graph、不回写索引状态缓存，意味着每次工作区扫描都是完整扫描，享受不到命令行工具第二次变快的收益。全部性能指标以此为前提。

### 5.7 崩溃隔离

宿主 release 配置为遇 panic 直接终止进程，一次 panic 会连带关闭便利贴、贴图、计时器等无关窗口。Mini-Git 解析的是用户机器上任意状态的仓库，风险高于其他模块。

落地手段：模块顶部声明 lint 禁止 `unwrap`、`expect`、`panic`、越界索引、未实现占位等写法，CI 以告警即失败的方式执行。这比文本扫描可靠——能区分注释与测试代码，并给出精确位置。

补充一组针对损坏仓库的接口级测试：对全部命令逐个调用，断言返回错误而非 panic。

**必须诚实记录该手段的边界**：lint 只覆盖本模块自身的源码，覆盖不到第三方绑定层内部的转换 panic（对象标识解析、字节到字符串转换等）。因此在当前的进程终止型 panic 配置下，「异常不导致宿主退出」是**通过代码纪律与测试把风险降到可接受**，而不是运行时保证。

两条路径供决策，需在实施前明确选定：

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| A. release 改为展开型 panic，工作线程捕获后转为错误码 | 该约束从「代码纪律」升级为「运行时保证」 | 二进制体积略增，优化面略窄；影响宿主全局配置 |
| B. 维持现状 | 无额外代价 | 该约束只是风险缓解，不构成保证；缺陷分级中 panic 即最高级，作为验收依据 |

现状文档按 B 表述。若选 A，本节与风险表需同步修订。

### 5.8 错误模型

错误码与需求文档附录 A 的 19 个场景**一一对应**，不可合并。命令层只返回错误码与必要参数，文案在前端按当前语言渲染。

```rust
pub enum MgError {
    // 仓库校验（对应附录 A 前 3 条）
    NotARepository,
    NotRepoRoot,
    BareUnsupported,
    // 仓库可访问性 —— 三者文案不同，不可合并为一个 RepoNotFound
    RepoPathMissing,        // 添加/进入时路径不存在
    RepoVanished,           // 使用中被移动或删除
    RepoCorrupted,
    // 权限 —— 普通权限与系统级授权的引导动作不同，必须区分
    PermissionDenied,
    MacosTccDenied,         // 引导至系统设置，对应 NFR-4.6
    // 文件
    FileNotFound,
    FileReadFailed,
    FileTooLarge { size: u64 },
    BinaryFile { size: u64 },
    DirReadFailed,
    // 差异
    DiffTimeout,
    DiffTooLarge,
    // 配置与快捷键（界面层产生，同享一套映射）
    ShortcutConflict { target: String },
    ShortcutRegisterFailed,
    ConfigWriteFailed,
    ConfigCorrupted,
    // 兜底
    Internal,
}
```

外部链接确认（附录 A 最后一条）是交互提示而非错误，由前端独立处理，不进入本枚举。

映射关系由一张表驱动，使「19 个场景各自映射到唯一文案键」与「文案不含底层技术信息」两项断言可以机械执行。

### 5.9 自定义协议

```
mini-git://<repo-token>/<url-encoded-rel-path>
mini-git://content/<content-token>
```

| 用途 | 说明 |
| --- | --- |
| 文件内容与图片 | 供查看区与 Markdown 相对路径图片使用 |
| 差异两侧文本 | 完整档的两份文本经令牌获取，不走 JSON 通道 |

**鉴权规则**：只接受当前已打开会话对应的仓库；路径规范化后必须仍位于仓库工作区内，拒绝任何穿越；令牌短时有效且与会话绑定。

### 5.10 路径规范化

路径规范化是四项需求的共同前提：仓库判重、会话按路径索引、跨平台文件匹配、去重展示。算法必须单一实现并以纯函数形式暴露供测试。

```
规范化(path):
  1. 解析符号链接，取真实路径
  2. Unicode 规范化为 NFC（macOS 文件系统返回 NFD，Windows 为 NFC）
  3. 分隔符统一为 '/'
  4. 仅在大小写不敏感的文件系统上做大小写折叠
     —— 不可无条件折叠：Linux 上 Repo 与 repo 是两个不同目录，
        无条件折叠会把它们错误判为同一仓库
  5. 去除尾部分隔符
```

第 4 步的平台条件是关键：无条件小写化是最容易写出的实现，但在大小写敏感的文件系统上会产生错误判重。

**对外暴露的相对路径一律以 `/` 分隔**，与仓库内部表示一致，复制到剪贴板的内容也遵循此约定，三平台一致。

**Windows 超长路径**：路径长度超过系统限制时，文件读取会失败。该失败按单文件错误处理，不影响同目录其他文件与其他功能区域。

### 5.11 边界仓库形态

| 形态 | 处理 |
| --- | --- |
| 空仓库 / unborn HEAD | `mg_repo_state` 返回 unborn 标记；引用树与提交列表走空状态；工作区差异以空树为基准，全部文件呈现为新增 |
| 根提交 | 父提交列表为空；差异以空树为基准 |
| 浅克隆 | 遍历到边界提交时，其父对象缺失。遍历器需在对象缺失时终止而非向上传播错误，界面展示到可达末端为止 |
| 合并 / 变基 / 拣选中间态 | `mg_repo_state` 返回状态枚举；冲突路径从状态扫描中单列 |
| 损坏仓库 | 错误按区域隔离：某个区域的读取失败只让该区域降级展示错误，其余区域继续工作。命令层不做全局熔断 |

分区降级是可靠性要求的落点：引用读取失败不应导致文件树不可用，反之亦然。前端每个数据区域独立持有自己的加载与错误状态。

#### 5.9.1 内容令牌的生命周期

差异的两侧文本经令牌传递，令牌背后是一份后端缓存。该缓存需要明确的边界，否则连续审阅大量文件会导致内存持续增长：

| 项目 | 规则 |
| --- | --- |
| 生成 | `mg_diff_prepare` 判定为完整档时写入缓存并返回令牌 |
| 内容 | 归一化后的两侧文本 |
| 键 | 会话标识 + 来源（工作区 / 提交哈希）+ 文件路径 |
| 有效期 | 60 秒；每次经协议取用时续期 |
| 容量上限 | 单会话 64 MiB，按最久未用淘汰 |
| 强制失效 | 会话释放、仓库刷新、工作区状态变更时清空对应来源的条目 |
| 并发 | 缓存由会话工作线程独占；协议处理器经通道取用，不直接持有 |

前端取完两侧字节后即可释放令牌引用；令牌过期后再次取用返回失效错误，前端重新发起 `mg_diff_prepare`。这一重试路径对用户不可见。

由于跨文件推进会连续产生令牌，缓存必须做淘汰而非只做过期——按最久未用淘汰保证连续审阅十余个文件时内存稳定。

**为什么不放宽全局资源协议作用域**：那等于把相应磁盘范围开放给所有窗口。新增专用协议只对 Mini-Git 窗口生效，边界清晰。

**为什么不走 JSON 通道**：2 MiB 源码经 JSON 转义后可膨胀到 3 MiB 以上，而差异视图需要传两份，单次调用可达 5–6 MiB，仅序列化就要数百毫秒。类型化绑定只承载元数据与轻量结构。

## 6. 前端设计

### 6.1 入口与路由

新增 `mini-git.html` 与 `src/mini-git-main.ts`，在构建配置的多入口中注册。

两项体积约束，都直接关系冷启动指标：

1. **不加载宿主的工具注册表**——那会把数十个工具的模块图拉进依赖树。
2. **不复用宿主的国际化实例**——宿主的国际化模块全量导入两种语言的完整文案（涵盖数十个工具）。现有精简入口直接导入该模块，等于白背这份资源的解析开销。Mini-Git 应建立独立的语言资源与独立实例。

两个路由：`/`（仓库选择）与 `/workspace`（审阅工作台）。

### 6.2 状态划分

| Store | 职责 | 持久化级别 |
| --- | --- | --- |
| `repos` | 仓库登记列表、最近打开时间、失效标记、上次退出落点 | L2 |
| `session` | 当前仓库的会话：Tab、树展开集合、分隔条、折叠态、推进游标、已查看标记 | L2 |
| `tabs` | 标签页集合与顺序、预览槽位、激活项、各自滚动位置 | 集合与顺序 L2；滚动位置 L1 |
| `gitdata` | 引用、提交分页缓存、**目录列举缓存**（按路径，展开后常驻至刷新或切换仓库）、状态扫描结果、差异结果缓存 | 不持久化 |

写盘时机：变更后防抖 1 秒；窗口隐藏时立即；宿主退出前立即。进程被强制终止时，最后一次防抖窗口内的变更允许丢失。

**切换仓库时的清理顺序**（顺序固定，不可调换）：

```
1. 递增 epoch —— 此后所有异步返回点先比对 epoch，不等则整体丢弃结果
2. 将当前仓库的 session 与 tabs 立即写盘（不等防抖）
3. 取消在途搜索，关闭该仓库的全部游标
4. 清空 gitdata（含差异缓存；对应的后端令牌随会话关闭失效）
5. 清空 tabs 运行态
6. 关闭后端会话
7. 打开目标仓库的后端会话
8. 加载目标仓库的持久化会话快照，渲染骨架屏
```

**第 1 步的 epoch 机制不可省略**。切换仓库时旧仓库仍有在途请求，其回包会把旧数据写进新仓库的状态——典型表现是切到 B 仓库后提交列表里混进 A 的提交。仅靠「清空再加载」挡不住迟到的响应。

第 3 步同样不可省略：游标与长任务持有工作线程资源，不显式关闭会在频繁切换仓库时堆积。

#### 6.2.1 窗口隐藏时的资源策略

界面状态必须完整保留，但后端缓存不必常驻——唤起后的指标只覆盖「可交互」，不覆盖数据重取。

| 时机 | 动作 |
| --- | --- |
| 隐藏时 | 取消在途的搜索与超大差异计算（用户已不在看）；停掉全部定时器（陈旧计时、刷新时间显示），唤起时重算而非后台累积 |
| 隐藏超过 30 分钟 | 释放非当前仓库的全部后端会话、全部内容令牌与后端差异缓存、前端差异解析缓存 |
| 唤起时 | 主动触发一次工作区状态刷新，与「距上次不足 3 秒跳过」的节流规则合流 |

#### 6.2.2 宿主退出前的写盘

「宿主退出前立即写盘」需要一个触发点，而宿主退出走的是进程直接退出路径，不逐窗口派发关闭事件——前端收不到任何通知，持久化数据只能靠防抖的那一秒。用户「改动后立刻退出」时，跨进程状态恢复的验收会失败。

需在宿主的退出请求处理中先拦截退出、向各窗口广播退出预告、给前端一个短窗口（不超过 200 毫秒或等待前端确认）后再真正退出。

若不实现该拦截，则须把防抖降到 250 毫秒，并在文档与验收标准中明确承认这一边界。二者必选其一。

数据损坏或结构不兼容时降级为默认值并给出一次性提示，不崩溃。配置结构带版本号，未知字段容错忽略。

### 6.3 标签页身份

唯一键为 `(rel_path, source)`，其中 `source ∈ { FileContent, WorkingDiff, CommitDiff(oid) }`。

| 规则 | 说明 |
| --- | --- |
| 同一文件的内容视图与差异视图是两个独立标签页 | 二者可同时打开，互切不销毁对方 |
| 标题默认为文件名 | 差异标签追加来源标识；同名时追加最短可区分父目录 |
| 悬停展示完整相对路径与来源 | |
| 预览槽位全局唯一 | 文件树单击与变更文件单击共用该槽位 |
| 数量上限与淘汰 | 标签页分「已固定」与「未固定」两类。预览槽位属未固定类，但未固定类不止它一个——用户可能通过多次操作产生多个未固定标签。超过 30 个时按最久未访问淘汰未固定类，已固定的永不自动关闭 |
| 转固定的五种触发 | 双击树项、双击预览标签、点击图钉、树内回车、双击变更文件项 |

### 6.4 审阅推进

推进游标与已查看标记是核心场景的关键状态，二者都进入会话持久化。

| 机制 | 规则 |
| --- | --- |
| 推进范围 | 当前变更文件集合，工作区改动与提交变更均适用 |
| 快捷键作用域 | Git 面板持有焦点时同样生效——用户是通过单击列表项进入差异的，此时焦点在面板而非查看区。若按严格作用域判定，核心场景的连续推进会当场断裂 |
| 越界行为 | 集合末尾继续推进时停留并提示，不回绕 |
| 标签页复用 | 推进期间复用同一预览槽位，不产生新标签页，不触发数量上限淘汰 |
| 已查看判定 | **差异内容全部进入过视口**即标记。不能用「滚动至底部」——AI 的典型改动每文件三五行，差异不足一屏、不产生滚动，那类文件将永远无法被标记 |
| 标记失效 | 仅失效内容已变化或已脱离集合的文件，其余保留。全量清空会让被打断的审阅必须从头再来 |

### 6.5 差异计算

**完整档由后端同时返回两侧完整文本与 hunk 边界**。差异计算在后端反正要跑一遍，把每个 hunk 的起始行与行数一并带回几乎是零成本。前端不做全文件行配对，只在 hunk 内部做细化：

```
后端 → 两侧完整文本 + hunk 边界列表
前端 ↓
1. 按 hunk 边界切分 → 未变更区来自完整文本，直接取用
2. hunk 内行配对 → 产出 (旧行号, 新行号, 类型) 序列
3. 修改行两两配对 → 词级行内差异；单行超过 10 000 字符时跳过
4. 折叠 → 变更处上下各留 3 行；连续未变更超过 8 行折叠，可展开
```

这一分工同时解决三个问题：

| 问题 | 解决方式 |
| --- | --- |
| 全文件配对的复杂度 | 行配对算法的代价随差异规模增长；两万行文件做全文件配对在纯 JS 上会远超差异计算的时限。改为按 hunk 切分后，总代价对**变更行数**线性，而非对文件行数 |
| 与 Git 真值的划分一致性 | hunk 划分直接来自底层库的计算结果，不需要用另一种语言的实现去对齐同一算法。前端只在 hunk 内细化，细化结果本就不参与真值比对 |
| 折叠区的原文 | 来自后端已返回的完整文本，无需额外请求 |

第 2、3、4 步为纯函数，在前端单测层以表驱动方式覆盖。

**hunk 内的细化仍放在 Worker 中执行**。单个 hunk 通常几十行，但一次差异可能有大量 hunk，累计仍可能产生可感知的阻塞帧。计算放入 Worker，主线程只接收结果并渲染。Worker 与主线程之间使用可转移对象传递文本，避免拷贝开销。

### 6.6 提交列表虚拟滚动

滚动流畅度指标要求 p95 帧时间不超过 20 毫秒，有两个前提必须在设计上保证：

1. **行高固定**：提交信息首行超长时截断而非换行。
2. **行内不做重计算**：时间格式化在数据进入 store 时一次性完成或缓存，不在渲染中执行。快速滚动时逐行格式化足以导致掉帧。

### 6.7 Markdown 渲染与资源

```
源码 → markdown-it → DOMPurify 净化 → 资源重写 → 挂载
                         │                  │
        剥离脚本、内联框架、对象、       相对路径 → 专用协议 URL
        嵌入、全部事件处理属性           外部 URL → 占位，不加载
                                        越界相对路径 → 拒绝并提示
```

SVG 一律以图片元素渲染，不内联为文档节点，从根上避免其中脚本的整类问题。

外部链接不在应用内加载；点击时首次确认后交由系统浏览器打开——这是「不发起网络请求」的唯一例外，且由用户显式触发。

## 7. 关键路径

### 7.1 进入仓库首屏

```
校验并建立会话
  ├─ 并行启动三路：
  │    ① 引用枚举 + 首批 100 条提交   → 目标 ≤ 500 ms（中档）
  │    ② 根目录列举（含忽略集合）      → 目标 ≤ 200 ms
  │    └─ ③ 工作区状态扫描             → 目标 ≤ 1.5 秒
  └─ ①② 完成即渲染首屏；③ 完成后填充改动数角标
```

**状态扫描不得阻塞首屏**。其成本与工作区文件数相关而非提交数：一个两百次提交但有八万个未忽略文件的仓库，扫描远超一秒；而十万提交的干净仓库反而很快。改动数角标允许延迟出现。

超出两万文件规模时降级为后台异步加载，并在扫描耗时超过两秒后自动将焦点刷新降级为仅手动刷新。

### 7.2 差异查看

```
点击变更文件
  → mg_diff_prepare 判档
  → 完整档：经协议取两侧原始字节 → 前端配对与行内高亮 → 渲染
  → 计算超过 300 ms 显示进度占位；超过 5 秒中止并提供「仍然生成」
```

### 7.3 刷新

| 触发 | 范围 | 约束 |
| --- | --- | --- |
| 手动（按钮 / 快捷键） | 引用、提交历史、工作区状态 | — |
| 窗口获得焦点 | **仅工作区状态** | 距上次不足 3 秒跳过；后台执行不阻塞界面；耗时超 2 秒的仓库自动降级为仅手动 |
| 陈旧提示 | 状态读取超过 60 秒时在变更区域提示 | 不做文件系统监听的必要配套——防止用户基于过期差异做出确认判断 |

#### 7.3.1 刷新必须显式刷新对象数据库

仓库句柄常驻不释放（见 5.1.3），而底层库会缓存对象数据库。用户在终端完成提交后回到界面按刷新，**新提交很可能读不到**——引用会按文件修改时间重读，但新写入的对象与打包文件需要显式刷新对象数据库才可见。

这是本模块最容易被误判为缺陷的一处：目标用户的典型流程正是「在终端完成提交」，核心场景走完必然触发。

刷新的后端入口必须依次执行：

```
1. 刷新该会话的对象数据库
2. 关闭当前游标（游标基于建立时的快照，不刷新会继续吐旧数据）
3. 按当前过滤条件新开游标，只重取第一页
4. 保留用户的选中项定位；选中项已消失时按相邻项降级
```

第 3 步只重取第一页而非恢复已加载的全部页：重建全部页会放大首次推进的代价，而用户刷新后的关注点通常在列表顶部。

`mg_log_open` 的语义写明：每次建立游标都取当前快照，不共享此前的遍历状态。

刷新后若选中项已消失，焦点移至位置最接近的相邻项而非跳回顶部，并给出可关闭的提示条。

## 8. 安全设计

| 面 | 措施 |
| --- | --- |
| 权限边界 | Mini-Git 窗口使用**独立的能力配置**，不复用宿主的默认配置。若复用，「不放宽全局作用域」将形同虚设。正向与否定清单见 8.1 |
| 内容安全策略 | Mini-Git 窗口的连接来源限定为进程间通道；图片来源不含 HTTP 与 HTTPS，仅允许专用协议与数据 URI |
| 资源访问 | 专用协议 + 会话绑定 + 路径穿越拒绝；不放宽全局资源作用域 |
| 渲染净化 | Markdown 经净化后挂载；SVG 以图片元素渲染 |
| 写入通道 | 窗口层禁用拖放；编辑器只读；无任何写入类 Git 调用 |
| 网络 | 无网络库；运行时可将网络 API 替换为抛错版本以供验证 |

### 8.1 能力配置管不到自定义命令

**这是本设计最容易误判的一处安全边界。** 框架的能力配置只约束核心命令与插件命令，**不约束应用自己注册的命令**。宿主现状即为证据：便利贴窗口的能力配置未授予任何应用命令权限，其前端照样能调用便利贴的自定义命令。

后果是双向的：

| 方向 | 风险 |
| --- | --- |
| 向外 | Mini-Git 窗口即便拿到最精简的能力配置，仍能调用宿主全部自定义命令——包括密码箱解密、环境变量写入、截图等 |
| 向内 | 宿主任意窗口都能调用 Mini-Git 的命令，绕开「仓库资源仅经受限协议暴露」的前提 |

**真正的边界是窗口标签守卫**：

```
全部 mg_* 与 resident_* 命令接收 webview 参数，
函数体首行统一调用 guard_minigit_window(&webview)，
断言发起窗口的标签为 mini-git，否则返回错误。
该参数不进入类型导出签名，前端无感知。
```

静态审计新增一条：模块内每个命令函数体首行必须是该守卫调用，与只读禁令共用同一套扫描器。

能力配置收紧的是**插件侧能力面**，窗口标签守卫覆盖的是**自定义命令面**，两者缺一不可。

### 8.2 内容安全策略只有全局一份

框架的安全策略配置是**全应用唯一**的一条，没有按窗口的配置项。因此：

1. **新协议必须加进全局策略**，否则同一份策略会挡掉 Mini-Git 自己的请求。需同时列出三种形态——不同平台的协议 URL 形式不同，只写其中一种会导致另一平台被挡。宿主现有的三个自定义协议只列了单一形态，这是既有隐患，Mini-Git 不应照抄。
2. 加进全局策略意味着**其他窗口在策略层面也能访问该协议**。这一层守不住边界。
3. **真正守住的是协议处理器自身的鉴权**：处理器可以拿到发起请求的窗口标签，须先断言标签为 Mini-Git 窗口，再校验令牌与路径。宿主现有协议实现忽略了该上下文参数，同样不应照抄。
4. 若确需按窗口收紧策略，唯一可行路径是在窗口构建时挂接资源请求回调，改写响应中的策略头。

### 8.3 能力清单

审计需要的是正向清单——只写「不含什么」无法逐项断言实际授予了哪些权限。

**需要授予**：

| 能力 | 用途 | 对应需求 |
| --- | --- | --- |
| 目录选择对话框 | 添加仓库 | FR-1.3 |
| 剪贴板写入 | 复制路径、复制哈希、复制变更文件路径列表 | FR-3.16、FR-4.11、FR-5B.7、FR-5D.6 |
| 外部打开 | 在默认程序中打开文件、外部链接交由系统浏览器 | FR-4.11、FR-10.5 |
| 自定义协议读取 | 文件内容与差异文本 | FR-10.1、FR-10.2 |
| 窗口控制 | 自绘标题栏的最小化、最大化、关闭 | FR-9.3 |

**明确不授予**：命令执行、文件系统写入、主目录读写、HTTP 请求、任意路径的资源协议访问。

剪贴板只需写入权限，不需要读取权限——测试中读取剪贴板走调试构建的测试桥，不通过生产权限。

**审计范围说明**：宿主自身含网络能力工具，产品级的「零网络」不成立。依赖与符号审计的范围限定为 Mini-Git 模块可达的依赖图与源码，不是全量依赖树。这也是 Git 绑定必须关闭默认 features 的原因之一——否则默认会引入 TLS 与 SSH 传输层，依赖审计从一开始就无法通过。

## 9. 可观测性与测试支撑

### 9.1 性能埋点

结构化单行 JSON，日志目录可由环境变量指定，便于测试前清空、测试后解析：

```json
{"evt":"perf","stage":"repo_open_first_paint","repo":"M","ms":412,"seq":3}
```

埋点阶段：窗口显示到首帧、仓库打开到首屏就绪、目录展开、提交翻页、差异计算。

日志解析器实现为纯函数，以样本文件在单测层验证格式契约；端到端层只验证五类阶段确实出现。

### 9.2 测试桥

沿用宿主既有的调试构建测试桥模式（调试构建 + 环境变量开启，正式构建中显式剔除该变量），扩展以下能力：托盘操作、窗口可见性查询、全局快捷键注册结果、剪贴板读取、逐帧采样。

不引入新的原生自动化框架。

### 9.3 配置目录隔离

配置路径需可由环境变量指定。没有这一项就无法准备「非法持久化文件」「旧版本结构」「不可写配置目录」等前置条件，也无法保证测试之间互不污染。

### 9.4 可测试性要求

| 要求 | 目的 |
| --- | --- |
| Git 能力以纯函数形式暴露（仓库路径 + 参数 → 结构化输出） | 使绝大多数逻辑可在集成测试层覆盖，不压到端到端层 |
| 前端七类纯逻辑不依赖组件 | 模糊匹配、自然排序、时间格式化、编码与二进制判定、Markdown 净化、差异配对、行内高亮 |
| 翻页返回遍历计数 | 使「耗时不随页码增长」可用确定性断言验证 |
| 状态与差异选项经专用构造函数产生 | 使「索引更新选项为关」可正向断言。**注意选项类型不提供读取接口**，正向断言只能在专用构造函数外包一层、由测试读取其底层标志位。若不接受该做法，则退回源码扫描的负向断言（禁止出现把该选项置为开启的写法），二者须择一并写入实现约定 |

## 10. 配置与构建改动

| 文件 | 改动 |
| --- | --- |
| `src-tauri/Cargo.toml` | 新增 Git 绑定依赖，**必须 `default-features = false`**（关闭默认的 HTTPS 与 SSH 传输层，使依赖审计可通过）；**并显式开启自带 C 源码编译**——否则在部分平台会链接到系统安装的版本，其默认参数与忽略语义可能不同，直接破坏「与 Git 真值比对」的可重现性 |
| `src-tauri/src/lib.rs` | 四处改动，缺一不可：① 模块声明；② 命令接入**运行时分发的累加器宏链**（新增一环并插入链中）；③ 命令接入**类型导出宏的两个条件编译分支**；④ 窗口事件处理的分支匹配——现有逻辑对未匹配的标签走「恢复窗口类」的兜底分支，Mini-Git 不显式加分支就会落入该分支，既拿不到「拦截关闭 + 隐藏」，还会被当作浮层处理。另需把「窗口尺寸适配屏幕」的逻辑从仅处理主窗口提取为通用函数，供窗口恢复路径复用 |
| `src-tauri/src/tray.rs` | 托盘菜单新增一项与对应的事件分支 |
| `src-tauri/src/shortcuts/` | 常驻窗口型工具的快捷键回调**直接在 Rust 侧打开窗口**，不经主窗口前端中转——现有工具快捷键的回调是向主窗口派发事件再由前端路由，Mini-Git 走这条链会凭空多一次跨进程往返，而唤起指标只有 200 毫秒预算 |
| `src-tauri/capabilities/` | 新增 Mini-Git 窗口的独立能力配置 |
| `src-tauri/tauri.conf.json` | 注册自定义协议；**全局内容安全策略中追加该协议的三种平台形态**（见 8.2）；不修改全局资源协议作用域 |
| `vite.config.ts` | 多入口新增 Mini-Git 条目 |
| `mini-git.html` | 新增精简入口页 |
| `src/tools/registry.ts` | 注册工具，标记为窗口形态 |
| `src/tools/interface.ts` | 元数据新增形态字段 |
| `src/locales/*.json` | 新增双语文案，两侧键集合须一致 |
| `.github/workflows/test.yml` | **新增**：仓库现有工作流仅在标签上构建，不执行任何测试 |

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Git 绑定的编译依赖 | 首次构建耗时增加，需 C 工具链 | 关闭默认 features 可去掉 TLS 与 SSH 依赖，编译链大幅简化 |
| 只读约束与性能的内在冲突 | 无法利用两类写入型缓存，扫描与遍历成本高于命令行工具 | 指标已按此前提设定；首屏拆分为不阻塞的三路；状态扫描超规模时降级 |
| `panic = "abort"` 下的崩溃连带 | 一次 panic 终止整个宿主 | lint 强制 + 损坏仓库的接口级测试；缺陷分级中 panic 即最高级 |
| 底层库不提供行内差异与行对齐 | 三条需求落在能力之外 | 完整档由后端给两侧原文、前端计算；超限降档 |
| 重命名检测静默失效 | 大规模重命名全显示为删除加新增，被误判为缺陷 | 超限时返回原因并在界面提示 |
| 提交信息编码 | 非 UTF-8 时绑定层返回空值，表现为整条空白而非乱码，极易漏测 | 按字节读取 + 依据编码头转码 + 有损兜底；「任何情况下不得出现空白提交信息」作为硬性判定 |
| 大档基准仓库的构建与存储 | 生成耗时以十分钟计，体积达 GB 级 | 不进 CI，在专用基准机常驻；CI 用精简档配合不变量断言 |
| 端到端框架能力不足 | 约五十条用例当前无法执行 | 已分为可跑、需扩展、人工三档，并列出基础设施依赖清单 |
| macOS 桌面自动化 | 驱动无对应实现，无解 | 该平台全部端到端用例归入人工回归 |

## 12. 实施顺序

按可独立验证的产出切分，前一阶段的产出是后一阶段的输入。

| 阶段 | 内容 | 可验证产出 |
| --- | --- | --- |
| 0 | 测试工作流 + 配置目录隔离 + 夹具生成脚本（首批）+ 真值固化 + **快照比对工具** | 测试在 CI 中可运行；夹具自检通过 |
| 1 | Git 绑定接入 + 类型与错误模型 + 只读审计测试 + lint 强制 + **只读挂载编排** | 只读禁令与崩溃隔离的强制手段先于业务代码就位；只读验收路径在第一行业务代码之前就能跑 |
| 2 | 后端读取能力：仓库、目录与忽略、引用、提交遍历、状态、差异、内容 + **第二批夹具**（差异档位、重命名、大量引用、大文件数） | 集成测试与真值比对通过 |
| 3 | 常驻窗口机制 + 独立入口 + 能力配置 + 自定义协议 | 空窗口可开关、隐藏后唤起瞬时恢复 |
| 4 | 仓库选择首屏 + 持久化 + 启动落点 | 可选仓库并进入工作台 |
| 5 | 三区布局 + 文件树 + 标签页 + 内容查看 | 可浏览文件 |
| 6 | Git 面板双 Tab：变更与历史 | 可看未提交改动与提交历史 |
| 7 | 差异视图 + 跨文件推进 + 已查看标记 | **核心场景跑通** |
| 8 | 刷新与陈旧提示 + 错误文案 + 国际化 + 主题联动 + 埋点 | 功能完整 |
| 9 | 性能调优 + 基准机验收 + 跨平台验证 + 人工回归 | 达到验收标准 |

阶段 0 与 1 前置于业务实现，是有意为之：只读约束与崩溃隔离一旦在后期补做，需要回头修改大量已写代码。只读挂载编排与快照比对工具同样前置——它们是只读验收的唯一执行路径，而只读违规是全局性的，发现得越晚返工面越大。

**尚待实测确认的事项**（不阻塞方案，但需在对应阶段第一件事解决）：

| 事项 | 阶段 | 影响 |
| --- | --- | --- |
| 提交遍历首次推进在大档仓库上的实际耗时 | 2 | 决定提交列表异步填充的界面反馈形态 |
| 工作区状态扫描在八万文件、开启实时防护的环境下的实际耗时 | 2 | 决定降级阈值取值 |
| 状态查询的路径限定剪枝在真实仓库上的实际收益 | 2 | 决定目录列举是否需要进一步优化 |
| 多窗口的自动化驱动能否枚举全部窗口句柄 | 3 | 决定多窗口测试走自动化还是测试桥 |
| 基准仓库生成脚本的实际耗时与产物体积 | 0 | 决定基准机的存储规划 |
